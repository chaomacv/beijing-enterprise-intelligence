# 从具体困难选择方法

本项目要回答两个问题：现成工具怎样组合成可运行流程；面对实际失败，为什么选择这一项修正。下面先记录 v0.2 的基础取舍，再记录本次全量处理遇到的新问题。

| 具体困难 | 当前选择与作用 | 已观察到的边界 / 扩展条件 |
| --- | --- | --- |
| 数千附件的格式与主题不一致 | Python 按文件签名识别；逐工作表生成文件名、表头、首中尾及随机样本卡片，再交给本地模型筛选 | 内容同质是抽样前提，不能证明没有罕见事件；独立标注后测漏筛，再决定是否加规则补扫、分组追加样本 |
| 原文敏感，不能依赖外部推理 API | 私有 Qwen3-8B、离线权重、本机服务、禁止云回退 | 8B BF16 在 24GB 显卡实测可运行；这证明能部署，不证明优于其他模型。更换模型应比较同一独立样本的错误和吞吐 |
| 一份表远超上下文窗口 | 完整记录分块，携带表头与文件语境；实际 tokenizer 检查输入、输出和余量，失败递归缩块 | 单条仍过长时明确复核，当前不声称任意长文本无损理解；确有此类需求再实现片段编号、重叠和跨片段合并 |
| 模型输出可能漏行、改字或引用错行 | JSON Schema 绑定当前批次的记录 ID、条数和字段名候选；逐条 ID 覆盖和指定源字段子串校验；无效输出不进入缓存 | 原文引用只能证明有来源，不能证明选对事件和角色；必须用独立标注检查语义 |
| 合成回归中高新认定被归为行业资质 | 明确本体边界：行业许可归 qualification，科技创新认定归 innovation；保留 proposed 阶段，再执行完整合成回归 | 分类边界应由业务定义明确，不能靠放宽验收或宣传准确率掩盖错误 |
| “拟认定名单”只有序号与企业名称 | 事件可引用受校验的原始标题，同时引用本行主体；保留 proposed 阶段 | 标题不能提供本行没有的代码、地址、金额或日期；遇到标题与行内结果冲突须复核 |
| 首轮模型过度使用 REVIEW | 将相关性筛选与身份核验分开说明，补充正反例；缺代码不等于没有主体 | 提示调整后的合成回归通过，不能据此宣布真实筛选准确率提高；下一步检查 KEEP 与 DROP 的独立样本 |
| 扩展名 CSV 实际为 Excel，RDF 看起来是空表 | 签名识别与全部工作表读取；识别 rdf:about 资源节点，非空未知 XML 复核；增加回归检查 | 两份真实 RDF 恢复 264 条记录。PDF、压缩包和复杂文档仍单独列为复核，不将它们算作已理解 |
| 15 条有效记录的 Excel 声明近百万行和上万列 | 重置只读工作表的声明范围，按 XML 实际坐标读取，去掉行尾空样式单元格并补齐表头内的空值 | 保留物理行号与非空值；同时用过大、过小声明范围检查防止虚假字段和漏行。方法参考 [openpyxl 只读工作表范围说明](https://openpyxl.readthedocs.io/en/stable/optimized.html) |
| 名称相近、同名或代码冲突 | 校验信用代码后优先关联；完整名称和非空地址一致才作弱证据关联；字符候选仅供复核 | 相似度不直接决定同一主体；向量召回可作为下一步实验，先测它能找回哪些当前漏掉的候选 |
| 中断、模型停机与重复执行 | 文件哈希、读取版本、提示词、本体及模型 ID 控制缓存；阶段落盘，模型失联停止 | 旧权重必须换服务模型 ID；有效缓存减少重算，REVIEW 保留且可重试；同一工作目录避免并发写入 |

标签目前覆盖处罚、异常经营、许可资质、科技认定、政策支持、采购中标、税务信用、环保监管和经营状态。标签描述观察到的事实，不生成银行授信决定；“未观察到”也不表示不存在。

后续实验按错误类型安排：漏筛先检查样本策略；漏提先检查上下文与证据契约；错配先检查角色和身份字段；吞吐不足先测分块、缓存和服务开销。只有这些调整仍不能解决具体问题时，再引入向量库、模型微调或更复杂的基础设施。

## 本次全量处理中的具体选择

| 遇到的实际问题 | 选择与验证 | 保留的限制 |
| --- | --- | --- |
| 已知记录超过四千万条，逐行让模型重抄结构化字段成本很高 | 本地模型规划主体字段、条件和阶段，程序逐行复制原值并校验；复杂文本仍交给本地模型 | 一个错误字段方案可能影响整表，保存完整方案及输入样本，矛盾阶段会拒绝并重试；仍需独立语义抽检 |
| libarchive 在非 UTF-8 成员名称处返回 bytes，36 个压缩包原先触发 TypeError | 解码时保留原路径字节的 Base64 与编码，并使用独立的安全输出目录；修复后重跑原始输入 | 不能按成员路径直接写入任意位置；嵌套、数量和展开字节量有限制，拒绝项保留台账 |
| 1,162 份非 RDF XML 无法按原有 record / row 读取 | 检查实际结构，按 XPath、重复节点索引和属性生成独立逻辑记录；没有把监测站数据误称为元数据 | 自动结构展开不代表银行业务相关，仍须文件筛选 |
| FileGDB 的组件单独打开没有业务含义 | 重建数据库目录，读取 3 个图层共 1,181 条属性记录；保留要素 ID、WKB 几何及 CRS | 组件与属性表分开计数，不把组件重复算作企业记录 |
| 影像及无原生文本 PDF 不能直接用表格读取器处理 | 本地 RapidOCR；保留页、文字框、置信度与原图关系，输出中明确 OCR_UNVERIFIED | OCR 不等于人工核验；事件阶段 confirmed 也不表示文字识别已经核实 |
| 多行表头进入约束生成后，JSON 字符串中出现未转义换行 | 仅允许解析字符串控制字符，再按标准 JSON 转义；实际字段值不变，随后仍做 Schema 与来源校验。4 个曾失败表回归通过 | 不修补缺失括号、编造字段或错误主体，其他无效输出仍进入重试／复核 |
| 合成方案把“已处罚”映射成 proposed，普通企业名映射成供应商 | 补充明确示例；校验阶段词与状态矛盾、无交易上下文的采购角色。处罚、检查合格、已认定、拟认定及统计排除回归通过 | 这些检查针对已发现错误，不能宣传为全量准确率 |
| 增加批量可能更快，也可能增加填充、约束生成开销 | 对同样 8 个合成请求比较：两批各 4 个共 26.184 秒，一批 8 个 32.423 秒；业务校验都通过。当前选择每批 4 个、4 GPU 独立副本 | 这是小型部署实测，不是可泛化吞吐基准；没有为了更大批量降低校验要求 |
| 首次并发导入 Transformers 时，某个客户端因 AutoTokenizer 懒加载竞争退出 | 初始化加锁，之后各客户端独立并行；4 个真实 tokenizer 的并发冷启动回归通过。任一工作线程异常会触发停止，避免其他线程继续运行时掩盖错误 | 停止后从已保存的逐表结果续跑，不重做已验证结果 |
| 长上下文混批多次触发显存不足，事后回退耗时 | 按实际 tokenizer 计算填充后的整批输入加输出预算，24,576 token 以上提前拆批；规划请求按表头与事件数量分组。缓存键和单个请求内容不变 | token 预算是当前 24GB 部署的保守调度值，并非显存占用的精确预测；仍保留失败缩批，单请求服务异常明确停止 |
| 数千文件和上万逻辑表的中间产物很难人工检查 | 九阶段目录、文件／表级 CSV 总表、逐条 JSONL、可查询 Parquet、阶段状态和最终数量对账 | 完整记录不应依靠电子表格界面的行数上限验收 |
| 实际文件中存在启发式未确认的表头，个别列名甚至呈现标题或文书号 | 保留原始候选及质量标记；聚合时按 scope_id 将标记带入台账、事件、来源和画像，去重也不丢来源标记；按表形成结构复核清单 | 未确认不等于已判错；不把结构不确定性当作企业业务风险。逻辑记录对账不等于物理行或语义已逐条核验 |

[逐阶段产物、状态和复现命令](full_corpus.md)。所有业务数据与模型请求／回复都保留在私有工作目录，公共仓库只发布实现、合成测试与汇总。
